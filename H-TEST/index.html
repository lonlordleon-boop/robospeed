トゥーンレンダリングは可能かTOON / CEL SHADING

「トゥーン風の見た目」と「トゥーンレンダリング（描画手法）」は別物なので、3層に分けて判定する。

やりたいこと可否実態
2Dのトゥーン絵 可能 プロンプトで指定するだけ。トゥーン専用モデルは存在しないが、どの画像モデルでも出る
トゥーン調テクスチャの3Dモデル 条件付き texture_prompt でセル調に寄せられるが、陰影がテクスチャに焼き込まれる
本物のトゥーンレンダリング 不可 光源に反応して陰が2値で切り替わる描画。シェーダー＝Unity側の領域

カタログを検索した結果、トゥーン／セルシェーディング専用の3Dモデルは存在しない。3D生成は全てPBR（物理ベース）前提。

Blender側では出来る。ただし持ち出せない

3D Jutsu は Blender 5.2 が動くため、Toon BSDF や Freestyle のアウトラインでトゥーンレンダリング自体は可能。ただしツール仕様に決定的な制約が明記されている。

プロシージャルシェーダーとワールドライティングは GLB に確実には引き継がれない

コミットされたシーンは Eevee と Khronos PBR Neutral で確定される

  • Blenderで組んだトゥーンシェーダーは、GLBに書き出した時点で消える。使い道は次の2つに限られる
  • レンダリング画像・動画としての書き出し（PNG/JPEG/MP4を最大8枚 publish 可能）→ カードイラスト、演出ムービー、資料用の絵には使える
  • .blendファイルのダウンロード（get_blend）→ トゥーンマテリアル込みで手元に持ってきて自分で調整する

Renderer Feature / 背面法
  • 最大の落とし穴：陰影の二重化。 AI生成テクスチャは陰影とAOが最初から絵に描き込まれているため、上からトゥーンシェーダーを当てると陰が二重になって濁る
  • 対策1：should_texture: false で白いメッシュだけ出し、Unity側で単色＋トゥーンシェーダー（原色メカとは特に相性が良い）
  • 対策2：テクスチャを使うなら texture_prompt に「flat cel-shaded colors, no shading, no ambient occlusion, uniform lighting」を明示して陰影を殺す

キャラメイク基盤は作れるかCHARACTER CUSTOMIZATION

MMORPG的に、身長・体型・髪型・顔・服を後から差し替えられる土台を Higgsfield × Unity で作れるか。

結論 ／ 用途の確定により更新
自作ツールが「開発用・非公開」であれば、VRoid素材を使って作ってよい。素材調達の問題は発生しない。
VRoidガイドラインの「ただし、あなたのみが個人的に使用するために制作する場合はこの限りではありません」に該当するため。そこで作ったキャラをゲームに焼き込んで配布・販売することも、元々明示的に許可されている。ツール側は例外条項、出力キャラ側は商用利用可で、両方ともクリアする。
ただし前提として
Higgsfield 単体でキャラメイク基盤を作ることは、依然として不可能。
「生成の単位」が根本的に合わないため。Higgsfieldの3D生成は「画像1枚 → 完結した1個のメッシュ」であり、キャラメイクが要求する「共通スケルトンに乗った分割パーツ群」とは設計思想が違う。以下の技術的分析は、自前でベースメッシュを用意する場合に必要となる。

キャラメイクに必要な技術要素と、その調達可否

実現したい操作技術的に必要なものHiggsfieldで出せるか
身長・体型のスライダー BlendShape（モーフターゲット）／ボーンスケール 不可 生成機能そのものが無い
顔立ちの変更 顔のBlendShape群 不可 同上
髪型・服の着せ替え パーツ分割メッシュ ＋ 共通スケルトン 不可 生成ごとに独立した骨が作られ、キャラと服で骨が一致しない
色・柄の差し替え 共有UVレイアウト／テクスチャアトラス 条件付き UVが毎回変わるためアトラス共有が困難
キャラ案の量産・決定 大量のコンセプトアート 得意 2cr/枚。ここが本来の主戦場

唯一の活路：3D Jutsu の Blender Python

Blender が丸ごと動くということは、プログラムでメッシュを分割し、リグを統一し、BlendShapeを付与できるということ。しかも glTF/GLB はモーフターゲットを正式にサポートしているため、BlendShape は理論上 Unity まで運べる。

  • bpy.ops.object.shape_key_add() — BlendShape の追加（体型・顔スライダーの土台）
  • アーマチュアモディファイアで複数メッシュを1つの骨に共有バインド（着せ替えの土台）
  • メッシュの分離・頂点グループ操作でパーツ化
  • 成果物は get_glb と get_blend の両方で取り出せる
  • 未検証の要点は2つだけ。ここが通るかで方針が決まる
  • ① BlendShape（shape_key）が GLB に乗って Unity まで届くか → 通れば体型スライダーが実現
  • ② 共通アーマチュアへの複数メッシュのバインドが GLB を通るか → 通れば着せ替えが実現

BOOTH等で購入した第三者素材の扱い

VRoid側のガイドラインは第三者素材について「そのデータのライセンスや利用条件に適切に従うこと」としており、判断は各出品者の規約に委ねられている。実態として規約は出品者ごとにバラバラで、購入額で完結するとは限らない。

よくある規約パターン内容
商用・ゲーム組み込み可ただしデータを容易に抽出できないよう保護することを条件とするものが多い
再配布禁止非常に多い。VRoid Hubへの投稿すら禁止の場合がある
商用ゲーム開発・販売を禁止原則禁止としている出品者も実在する
事前連絡・許諾が必要個人配信を超える商用利用はDMでの確認を求める形式
クレジット表記必須商用・ゲーム利用時に明記を要求
  • 最大の争点は「ゲームに組み込む＝モデルデータを配布する」ことに当たる点。多くの規約が再配布を禁止しているため、購入しただけでは足りない
  • 購入前に確認すべき3点 — ① 商用利用可か　② ゲーム/アプリへの組み込みが明示的に許可されているか　③ 再配布の扱い（アプリ内保護を条件に可、など）
  • 方針：主人公など中核キャラはVRoid標準アイテム＋自作テクスチャで固め、BOOTH素材はサブキャラや検証用に留める。権利確認のコストとリスクを負わずに済む

MCP連携はどこまで可能かMCP INTEGRATION

Higgsfield → VRoid → Unity のパイプラインを、どこまでAIから駆動できるか。

結論
VRoid Studio だけは直結できない。だが前後（Higgsfield と Unity）は両方MCPで繋がる。
VRoid Studio は API も CLI も持たないGUIアプリのため、外部から操作する公式手段が存在しない。一方 Unityには2026年6月に公式MCPサーバーが追加されたため、パイプラインの出口側は完全に自動化できる。
対象MCP連携実態
Higgsfield 接続済 本レポートの通り。生成側は既に稼働中
VRoid Studio 本体 不可 API・CLI・公式プラグイン機構のいずれも無い。非公式拡張（VRoidXYTool）は存在するが外部制御用ではない
Unity Editor 公式対応 2026年6月にUnity公式MCPサーバーが追加。unity mcp configure claude-code で接続。シーン検査、コンソール読み取り、スクリプト編集、Editorアクション実行が可能
VRMファイル 間接的に可 VRMはglTFベースの公開仕様。Blender用VRMアドオンやPythonスクリプトで機械的に操作できる（VRM4U / VReducer 等の前例あり）
VRoid Hub API有り OAuth 2.0 と開発者登録が必要。Unity/UE向けSDKも提供。モデルの取得用であり、キャラメイクの自動化用ではない

標準アイテム（髪型・服）の種類と幅BOOTH素材に頼らず、標準の範囲だけでどれだけ作り分けられるか。権利確認のコストを回避できるかに直結
テクスチャの読み込み・書き出し対応していれば Higgsfieldで生成したテクスチャを持ち込める。連携点になる
1体あたりの作成時間敵キャラの量産が現実的かの判断材料。ここが重ければ自作ツールの動機になる
出力VRMのポリゴン数スマホ向けの場合に効いてくる。多ければ減らす工程が要る
体型を変えた複数モデルの骨格共通ならパーツ差し替えが成立する。自作ツールを作る場合の前提条件
  • 自作ツールが必要になるのは、次のいずれかに当たった場合。そうでなければ作らない方がよい
  • ゲーム内でリアルタイムに見た目を変える必要がある（装備が外見に反映されるなど）
  • 敵キャラを大量にバリエーション生成したく、VRoidでの手作業では追いつかない
  • VRoidの表現範囲を超える造形が中核に必要（メカ、人型でないモンスターなど）
